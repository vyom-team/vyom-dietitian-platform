# Organization onboarding

How a newly registered user becomes the owner of a practice.

---

## Organization is the tenant; "practice" is the word users see

One entity, two names, on purpose:

| Database | Interface |
|---|---|
| `Organization` | Practice |
| `OrganizationMember` | Team member |
| `OWNER` | Practice owner |
| `DIETITIAN` | Dietitian |
| `RECEPTIONIST` | Receptionist |
| `CLIENT` | Client |
| `SUPER_ADMIN` | (internal, never shown) |

The database keeps the tenant-neutral name because that is what it *is* — a
solo practitioner and a twelve-person clinic are the same structure. The
interface says "practice" because that is what a dietitian calls their business.
Nobody using the product should ever encounter the words *organization*,
*tenant*, or *organization_id*.

**Do not rename the models.** The split is deliberate and the schema comments
say so.

---

## The flow

```
register → confirm (if enabled) → sign in
    ↓
DAL reads memberships
    ↓
memberships.length === 0  →  /onboarding
    ↓
  step 1  practice details
  step 2  owner profile
  step 3  review
    ↓
createPracticeAction  (Server Action)
    ↓
createPractice  (service, one transaction)
    ↓
Organization + OrganizationMember(OWNER) + Subscription(FREE/TRIALING)
    ↓
/dashboard
```

### Onboarding is defined by data, not a flag

There is no `onboarding_completed` column. The presence of a membership row *is*
the definition of "onboarded":

```
memberships.length === 0   →  onboarding
memberships.length  >  0   →  application
```

A separate flag would be a second source of truth, and second sources of truth
drift. This one cannot: the thing onboarding produces is the same thing that
decides whether onboarding is needed.

### Why there is no redirect loop

Two guards in `src/lib/auth/dal.ts`, exact mirrors of each other:

| Guard | Used by | Sends away |
|---|---|---|
| `requireOnboardingAccess()` | `/onboarding` | user *with* a practice → `/dashboard` |
| `requireMembership()` | dashboard routes | user *without* a practice → `/onboarding` |

For a signed-in user the two conditions are total and disjoint — exactly one
holds — so each guard redirects to a route the other accepts. A loop is not
merely unlikely; it is unrepresentable.

Both run on the server before anything renders, so there is no flash of
onboarding for a user who already has a practice.

## Security

The whole design rests on one idea: **the values an attacker would want to
control are not part of the input.**

A Server Action is a public HTTP endpoint. Anyone can post to
`createPracticeAction` without ever loading the wizard. So of the four things
that matter — who the owner is, which organization, what role, what slug — none
is accepted from the request:

| Value | Where it comes from |
|---|---|
| Owner (`userId`) | The verified session, via `requireAuth()` |
| Role | Hard-coded `OWNER` in the service. Not a parameter. |
| Organization id | Generated by the database |
| Slug | Derived server-side from the name |
| Status | Schema default `ACTIVE` |

`createPracticeSchema` has no `role`, `userId`, `organizationId`, `slug`, or
`status` field, so Zod strips them. There is no request shape that asks to be a
`SUPER_ADMIN`, and none that makes someone else the owner. This is tested:
injected values are asserted absent from the parsed payload.

`SUPER_ADMIN` is additionally excluded from `ASSIGNABLE_ORGANIZATION_ROLES`
(see [security.md](security.md)), so no organization-facing code can grant it
even by mistake.

### Replay protection

The action re-checks membership immediately before writing, not only in the page
guard — a direct POST never renders the page. If a race slips through, the
service checks again, and a second practice for the same owner is refused.

### Slug safety

The slug reaches URLs, so the output alphabet is the control: `[a-z0-9-]` only.
Path traversal, scheme injection, and query smuggling are structurally
impossible rather than filtered case by case. Reserved words (`admin`, `api`,
`login`, …) are rejected so a practice cannot shadow an application route or
make a convincing phishing path.

Uniqueness is settled by the database, not by a check-then-insert: candidates
`base`, `base-2`, `base-3`… are tried against the unique index until one wins.
Two people registering the same practice name simultaneously both succeed, with
different slugs.

### Prisma still bypasses RLS

Unchanged from Phase 3 and worth repeating: Prisma connects as the table owner,
so policies do not constrain it. The DAL is what authorizes server-side work.
Phase 4 adds no new privileged path — the organization service runs as the
normal application user and touches only rows belonging to the caller.

No RLS policy was weakened, and no service-role key is used anywhere.

## The transaction

Organization, membership, subscription, and the owner's profile update happen in
one `prisma.$transaction`. All four or none.

A practice with no owner would be unreachable — nobody could administer it — and
an owner row pointing at a missing organization breaks every membership lookup.
A partial success is worse than a clean failure, so failure is the only
alternative offered.

Verified by test: a transaction forced to fail after the organization row is
written leaves no organization behind.

## Initial subscription

`FREE` / `TRIALING`, with `trialStartsAt` set. Both values already existed in the
Phase 2 schema; nothing new was invented.

Deliberately absent: pricing, plan limits, trial length, payment provider ids.
Those belong to the billing phase, and guessing a trial length now would bake in
a number nobody has decided.

## Data captured

**Step 1 — practice.** Name, country, timezone (required); email, phone,
website, address (optional).

- **Country** is stored as ISO 3166-1 alpha-2, not a display name — codes are
  stable across locales. Names are rendered from `Intl.DisplayNames`.
- **Timezone** is an IANA identifier. Abbreviations are rejected: ICU silently
  resolves `IST` to `Asia/Calcutta` and `EST` to `America/Panama`, which does
  not observe daylight saving. A practice storing "EST" would drift by an hour
  for half the year.
- **Website** accepts `http:` and `https:` only. `javascript:` and `data:` URLs
  would turn a stored practice profile into an XSS vector for anyone clicking
  the link.

> Runtime note: some ICU builds list `Asia/Calcutta` and omit both
> `Asia/Kolkata` and `UTC` from `Intl.supportedValuesOf('timeZone')`. Both are
> added explicitly, otherwise the default value would be missing from the picker
> for Indian practitioners. A test pins this.

**Step 2 — owner profile.** Full name (required); professional title, phone, bio
(optional). This *updates* the profile the auth trigger already created; it never
creates a second identity. Professional title is free text because credentials
vary by country and registering body.

**Logo upload is deferred.** Supabase Storage is not configured, and a fake
uploader would be worse than none. Base64 images in Postgres were never an
option.

## Wizard state

State lives in React for the duration of the flow and is submitted once, at the
end. Nothing is written to `localStorage` — the flow is short, and a
half-finished practice profile sitting in browser storage on a shared machine is
needless exposure. A refresh restarts the wizard; going back preserves what was
entered.

The steps validate in the browser for feedback, but the Server Action
re-validates the complete payload. The step-by-step validation is a convenience;
the server's copy is the one that decides.

---

## Multiple practices

The schema has always supported one person belonging to several organizations —
that is why membership is its own table rather than a column on `UserProfile`.

Phase 4 allows **one practice per person**, enforced in the service. That is the
replay guard, not an architectural limit: without it, re-posting the final step
would silently create a second practice. Lifting the restriction later means
relaxing one check and adding a practice switcher; no migration, no re-modelling.

---

## Future audit events

Audit logging is not built yet. When it is, organization creation produces two
events worth recording:

- `organization_created` — who, when, which practice
- `organization_owner_assigned` — who was granted OWNER, by what path

Both matter because they are privilege-granting operations.
