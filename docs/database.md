# Database

How Vyom's database is put together, and how to work with it locally.

---

## 1. Architecture

```
Next.js (server only)
      ↓
Prisma Client 7  +  @prisma/adapter-pg
      ↓
PostgreSQL 17 (Supabase Cloud)
```

Supabase is the managed PostgreSQL provider. Nothing is self-hosted, and there
is no second database.

**Organization is the tenant.** Every piece of practice data belongs to an
organization, and isolation between organizations is the platform's most
important security property.

```
Organization (tenant)
  ├── OrganizationMember ── UserProfile
  └── Subscription
```

---

## 2. What Supabase provides

| Now | Later |
|---|---|
| PostgreSQL hosting | Supabase Auth (Phase 3) |
| Connection pooling | Row Level Security (Phase 3) |
| Backups | Storage for logos and PDFs |

At this stage Supabase is used **only as the Postgres provider**. Supabase Auth
is not wired up, and no RLS policies exist yet.

---

## 3. What Prisma provides

Schema definition, migrations, a typed client, and Studio. Prisma owns the
`public` schema; Supabase owns `auth` and `storage`, which Prisma does not
manage or migrate.

### Prisma 7 specifics

Prisma 7 differs from most tutorials online, which target 6.x:

- **Driver adapter required.** SQL databases go through `@prisma/adapter-pg`
  backed by `pg`. There is no built-in query engine binary to configure.
- **Connection URL lives in `prisma.config.ts`,** not in `schema.prisma`. The
  datasource block declares only the provider.
- **`directUrl` no longer exists** in the datasource config. The pooled/direct
  split is expressed by pointing each consumer at a different variable — see
  below.
- **Client output path is explicit.** It generates to `src/generated/prisma`,
  which is git-ignored and rebuilt by `postinstall`.

---

## 4. Connections: two URLs

| Variable | Port | Used by | Why |
|---|---|---|---|
| `DATABASE_URL` | 6543 | The application at runtime | Serverless functions open many short-lived connections; the pooler absorbs them. |
| `DIRECT_URL` | 5432 | The Prisma CLI for migrations | Migrations issue DDL and hold advisory locks, which do not survive a transaction-mode pooler. |

`prisma.config.ts` reads `DIRECT_URL ?? DATABASE_URL`, so a plain local Postgres
with no pooler works with `DATABASE_URL` alone.

Both are secrets. Neither may ever be given a `NEXT_PUBLIC_` prefix.

Find them in Supabase under **Project Settings → Database → Connection string**.

## 5. Conventions

| Layer | Style | Example |
|---|---|---|
| Prisma model | PascalCase singular | `OrganizationMember` |
| Table | snake_case plural | `organization_members` |
| Prisma field | camelCase | `organizationId` |
| Column | snake_case | `organization_id` |
| Enum type | snake_case | `organization_role` |

The mapping is explicit via `@map` / `@@map`. Application code reads naturally
in TypeScript while the database keeps idiomatic SQL naming — no quoting of
mixed-case identifiers in raw queries.

### Identifiers

UUIDs everywhere, generated by PostgreSQL via `gen_random_uuid()`.

Generating in the database rather than the application means an ID exists even
for rows inserted by SQL or another service. Sequential integers are avoided
because they leak business volume and are trivially guessable in URLs — a real
concern for a product whose URLs will reference client records.

### Timestamps

Every entity carries `created_at` and `updated_at` as `timestamptz(6)`.

`timestamptz` stores an absolute instant; the database normalises to UTC and
converts on read. Formatting to the practitioner's local timezone is a UI
concern and never changes what is stored. Never use plain `timestamp`.

## 6. Models

### Organization

The tenant — one practice or clinic. Owns members, subscription, and every
future piece of practice data.

`slug` is unique platform-wide and safe for URLs. `status` is
`ACTIVE | SUSPENDED | ARCHIVED`; `archived_at` records when archival happened.

### UserProfile

A person. **Holds no credentials of any kind** — no password, hash, OTP, or
session token. Supabase Auth owns authentication.

`auth_user_id` will hold the `auth.users.id` UUID from Supabase. It is nullable
because a profile can be created by invitation before that person signs up, and
it is not a Prisma relation because `auth.users` lives in a schema Prisma does
not manage. Phase 3 completes the linkage.

### OrganizationMember

Joins a person to an organization and carries their `role` and `status`.

Membership is a separate table rather than an `organizationId` column on
`UserProfile` so one person can belong to several organizations — a consulting
dietitian working with two clinics — without a later migration.

Roles: `SUPER_ADMIN`, `OWNER`, `DIETITIAN`, `RECEPTIONIST`, `CLIENT`. These are
declared but **not enforced**; authorization arrives in Phase 3. There is no
permission table, and none is planned until the product needs finer grain than
a role.

### Subscription

Belongs to the organization, never to a user, so commercial ownership survives
a change of practitioner. One row per organization, whose `plan` and `status`
change over time.

Plan limits and prices are configuration, not schema — nothing hard-codes
behaviour against these enum values. Payment-provider identifiers are added by
the billing phase.

## 7. Relationships and delete behaviour

| Relation | Cardinality | On delete |
|---|---|---|
| Organization → OrganizationMember | 1 : n | `Cascade` |
| UserProfile → OrganizationMember | 1 : n | `Restrict` |
| Organization → Subscription | 1 : 1 | `Cascade` |

**Why they differ.** Cascade from the organization is scoped: removing a tenant
removes its membership rows and subscription, which are meaningless without it.
Restrict on the user is protective: a person's profile cannot be deleted while
they still belong to an organization, so history never ends up pointing at a
missing author.

### Deletion strategy

**Prefer archival over deletion.** This is healthcare-adjacent software with
retention obligations, and clinical history must not vanish because someone
clicked delete.

- Organizations are archived — `status = ARCHIVED` plus `archived_at` — not
  deleted. No production code path deletes an organization.
- Memberships are revoked by setting `status = REMOVED`, preserving the record
  that the person once had access.
- Cascade rules exist as a database-integrity backstop for genuine hard deletes
  (a mistaken signup, a GDPR-style erasure request), not as the normal path.

When client and log tables arrive, they follow the same rule: archive, don't
delete.

## 8. Indexes

Every index below earns its place; none is speculative.

| Index | Purpose |
|---|---|
| `organizations_slug_key` (unique) | Slug lookup on every tenant-scoped request, and the uniqueness guarantee. |
| `organizations_status_created_at_idx` | Admin listing of active organizations by recency. |
| `user_profiles_email_key` (unique) | Login and invitation lookup; one profile per address. |
| `user_profiles_auth_user_id_key` (unique) | Maps a Supabase Auth user to a profile in Phase 3. |
| `organization_members_organization_id_user_id_key` (unique) | One membership per person per organization. |
| `organization_members_organization_id_role_idx` | "Who is in this organization", filtered by role — team lists and permission checks. |
| `organization_members_user_id_idx` | "Which organizations does this person belong to" — runs on every sign-in. |
| `subscriptions_organization_id_key` (unique) | One subscription per organization. |
| `subscriptions_status_trial_ends_at_idx` | Platform sweeps for expiring trials and past-due accounts. |

Primary keys are indexed automatically and are not listed.

## 9. Multi-tenancy rule

**Every future organization-owned table must carry an `organization_id` column,
a foreign key to `organizations`, and an index on it.**

That covers clients, intake records, plans, meals, logs, reports, and anything
else added later. A tenant-owned table without `organization_id` cannot be
isolated by RLS and is a security defect, not a style preference.

Reference data shared across all tenants — the IFCT food table, for instance —
is the exception and carries no `organization_id`.

---

## 10. Future RLS strategy

Row Level Security is **not implemented yet**, deliberately: policies must key
off the authenticated user, and authentication does not exist until Phase 3.
Half-written policies would give a false sense of protection.

The intended approach, for Phase 3 to implement:

1. Enable RLS on every tenant-owned table.
2. Derive the current user from the Supabase JWT (`auth.uid()`).
3. Resolve that user's organization memberships.
4. Restrict every row to organizations the user belongs to.
5. Enforce role rules on top of tenant scope — a `CLIENT` sees only their own
   records, not the whole organization's.
6. Keep the service-role key server-side only; it bypasses RLS entirely.

RLS is defence in depth, **not** a replacement for authorization checks in
application services. Both layers are required; neither alone is acceptable.

## 11. Migration workflow

Migrations are committed to git and are the only sanctioned way the schema
changes. Never edit the database by hand behind Prisma's back.

```bash
# 1. Edit prisma/schema.prisma
# 2. Create and apply a migration
npm run db:migrate            # prisma migrate dev

# 3. Review the generated SQL in prisma/migrations/<timestamp>_<name>/
# 4. Verify
npm run db:verify

# 5. Commit schema + migration together
```

In production/CI, apply already-reviewed migrations without generating new ones:

```bash
npm run db:deploy             # prisma migrate deploy
npm run db:status             # check for drift
```

`db:migrate` is a development command. Never run it against production.

## 12. Local development

```bash
cp .env.example .env.local    # fill in DATABASE_URL and DIRECT_URL
npm install                   # postinstall generates the Prisma client
npm run db:migrate            # apply migrations
npm run db:seed               # optional development fixtures
npm run db:verify             # confirm the foundation works
npm run db:studio             # browse data
```

Visit `/system` in the running app for a connection status page.

| Script | What it does |
|---|---|
| `db:generate` | Regenerate the Prisma client after a schema change |
| `db:migrate` | Create + apply a migration (development) |
| `db:deploy` | Apply existing migrations (production/CI) |
| `db:status` | Report migration state and drift |
| `db:studio` | Open Prisma Studio |
| `db:seed` | Insert development fixtures (idempotent) |
| `db:verify` | Assert constraints, keys, and indexes are enforced |

### Resetting

`prisma migrate reset` **drops all data**. It is fine against a personal
development database and must never be pointed at staging or production. There
is deliberately no npm script for it, so it cannot be run by muscle memory.

## 13. Seed data

`prisma/seed.ts` creates a "Development Practice" organization, a
`dev@vyom.local` user, an `OWNER` membership, and a `FREE` trial subscription.

Everything is obviously synthetic so it can never be confused with customer
data. The seed refuses to run when `NODE_ENV=production`, and every write is an
upsert, so it is safe to re-run.

It creates **no clients, no health information, and no nutrition values**. Those
must come from real records and approved reference sources (IFCT 2017,
ICMR-NIN 2020) — never from a seed file.

## 14. Security

- `src/lib/prisma.ts` and `src/config/env.server.ts` both start with
  `import "server-only"`. Importing either from a client component is a build
  error, so a connection string cannot reach the browser bundle.
- Client-safe configuration lives in a separate module, `src/config/env.ts`,
  which contains only `NEXT_PUBLIC_*` values.
- `.env` and `.env.local` are git-ignored; `.env.example` carries placeholders
  only and never real values.
- The Prisma client is created lazily and cached on `globalThis` in development,
  so hot reload does not exhaust the connection pool.
- `/system` reports reachability and migration count only — never the host,
  credentials, or raw driver errors. Full errors go to the server log.
- No public API route exposes database information.

---

## 15. Schema evolution

The schema grows one phase at a time. Phase 2 covers only the core SaaS
entities; clients, intake, nutrition targets, foods, plans, meals, and logs are
each added by the phase that owns them.

This avoids guessing at fields years before the requirements are known, which is
how schemas end up with columns nobody can explain.
